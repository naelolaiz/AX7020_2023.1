Key Debounce Experiment
========================

**The experiment Vivado project is "key_debounce".**

This article mainly explains the principle of key debouncing and program development. The program increments a number by 1 when a key is pressed, displays the result on LEDs, and is compiled and debugged using Vivado software.

Experiment Principle
--------------------

As a basic human-machine input interface, keys can be found in many electronic designs. Due to mechanical characteristics, when a key is pressed or released, the key input value will bounce. No matter how steadily the key is pressed, it is difficult to eliminate the bouncing. There are many ways to debounce keys, and this experiment mainly uses FPGA timing for debouncing. In the experiment, a counter is designed. When the key input changes, the counter is cleared to zero; otherwise, it accumulates until it reaches a preset value (e.g., 10ms), at which point the key is considered stable and the key value is output, thus obtaining a debounced key value. Since rising edge and falling edge detection of keys is needed in many places, the key debounce module directly integrates rising edge and falling edge detection functionality.

Key debounce module (ax_debounce) ports

The LED display part will not be explained in this chapter. Here we will provide some explanation of the key debounce module "ax_debounce" in the example. The module uses two-stage D flip-flops to latch the key value, and the key value is only output when it is stable. We can see in the assign statement that there is an "assign
a_reset = (DFF1 ^ DFF2)". Anyone who has studied digital circuits should know that "^" is the XOR operator, where the result is 0 when both sides are the same, and 1 when they are different. In the program, the result of the comparison between DFF1 and DFF2 is assigned to "a_reset" via "assign", which checks whether the values of the two consecutive stages of registers that latch the key value are consistent. Only when the values of both stages are consistent, i.e., when the value of a_reset is 0, does it indicate that the currently latched key value has not changed. When the counter accumulates to "TIMER_MAX_VAL", it indicates that the latched key value has been stable and can be output. Additionally, in the module we can see the "{.......}" symbol. Note that this is not just curly braces -- it represents the bit concatenation operator, which concatenates two or more signals together. Please refer to the example for specific usage.

.. code:: verilog

 `timescale 1 ns / 100 ps
 module  ax_debounce 
 (
     input       clk, 
     input       rst, 
     input       button_in,
     output reg  button_posedge,
     output reg  button_negedge,
     output reg  button_out
 );
 //// ---------------- internal constants --------------
 parameter N = 32 ;           // debounce timer bitwidth
 parameter FREQ = 50;         //model clock :Mhz
 parameter MAX_TIME = 20;     //ms
 localparam TIMER_MAX_VAL =   MAX_TIME * 1000 * FREQ;
 ////---------------- internal variables ---------------
 reg  [N-1 : 0]  q_reg;      // timing regs
 reg  [N-1 : 0]  q_next;
 reg DFF1, DFF2;             // input flip-flops
 wire q_add;                 // control flags
 wire q_reset;
 reg button_out_d0;
 //// ------------------------------------------------------
 
 ////contenious assignment for counter control
 assign q_reset = (DFF1  ^ DFF2);          // xor input flip flops to look for level chage to reset counter
 assign q_add = ~(q_reg == TIMER_MAX_VAL); // add to counter when q_reg msb is equal to 0
     
 //// combo counter to manage q_next 
 always @ ( q_reset, q_add, q_reg)
 begin
     case( {q_reset , q_add})
         2'b00 :
                 q_next <= q_reg;
         2'b01 :
                 q_next <= q_reg + 1;
         default :
                 q_next <= { N {1'b0} };
     endcase     
 end
 
 //// Flip flop inputs and q_reg update
 always @ ( posedge clk or posedge rst)
 begin
     if(rst == 1'b1)
     begin
         DFF1 <= 1'b0;
         DFF2 <= 1'b0;
         q_reg <= { N {1'b0} };
     end
     else
     begin
         DFF1 <= button_in;
         DFF2 <= DFF1;
         q_reg <= q_next;
     end
 end
 
 //// counter control
 always @ ( posedge clk or posedge rst)
 begin
 	if(rst == 1'b1)
 		button_out <= 1'b1;
     else if(q_reg == TIMER_MAX_VAL)
         button_out <= DFF2;
     else
         button_out <= button_out;
 end
 
 always @ ( posedge clk or posedge rst)
 begin
 	if(rst == 1'b1)
 	begin
 		button_out_d0 <= 1'b1;
 		button_posedge <= 1'b0;
 		button_negedge <= 1'b0;
 	end
 	else
 	begin
 		button_out_d0 <= button_out;
 		button_posedge <= ~button_out_d0 & button_out;
 		button_negedge <= button_out_d0 & ~button_out;
 	end	
 end
 endmodule

Finally, what needs to be explained in the program are the two output signals "button_posedge" and "button_negedge". This is a commonly used method for capturing rising and falling edges. The RTL view it describes is as follows:

.. image:: images/11_media/image3.png
      
Of course, there are other methods for describing edge detection circuits, but the basic principle is the same: in a sequential logic circuit, the signal to be detected is first assigned as input to a custom register using non-blocking assignment, and then by comparing the values of two consecutive stages of registers, it is determined whether it is a rising edge or falling edge. A change from 0 to 1 is a rising edge, and a change from 1 to 0 is a falling edge.

Simulation
----------

Here we have added a stimulus program file key_debounce_tb.v to simulate the key input.

The simulation results are as follows. We can see that the key was pressed a total of 5 times, but because the low-level hold time of the first 4 key presses was less than 20ms, these 4 presses were determined by the program to be bouncing. Only when the 5th key press duration exceeded 20ms was it recognized as a valid key press, and at that point the LED status changed.

.. image:: images/11_media/image4.png
      
Similarly, after the key is released, the program also checks whether the high-level hold time exceeds 20ms. Because the first 4 high-level periods were all less than 20ms, the program treated them as key bouncing. Only when the 5th high-level hold time exceeded 20ms did the q_add signal change.

.. image:: images/11_media/image5.png
      
Experiment Result
-----------------

After powering on the development board and downloading the program, press the "PL KEY2" button, and you can see the 4 LEDs change, corresponding to binary data, incrementing by one with each press. Without debouncing, it would be impossible to achieve incrementing by one per press.
