I2C Interface EEPROM Experiment
================================

**The Vivado project for this experiment is "i2c_eeprom_test".**

This experiment uses an I2C master controller from the open-source website OpenCores to control the reading and writing of an I2C interface EEPROM, practicing how to effectively use open-source code to improve development efficiency.

Experiment Principle
--------------------

On the development board, the FPGA chip is connected to the EEPROM 24LC04 via the I2C bus. Each of the two I2C bus lines is pulled up to 3.3V through a 4.7K resistor, so when there is no output on the bus, it will be pulled high.
The write protection of the 24LC04 is not enabled; otherwise, the FPGA would be unable to write data. Since A0~A2 are all tied low in the circuit, the device address of the 24LC04 is 0xA0.

I2C Bus Protocol and Timing
----------------------------

The I2C standard rate is 100kbit/s, with a fast mode of 400kbit/s. It supports multi-device communication and multiple master modules, but only one master is allowed at any given time. The serial bus consists of the data line SDA and the clock line SCL; each circuit and module has a unique address.

Here we use the AT24C04 as an example to illustrate the basic operations and timing of I2C read/write. I2C device operations can be divided into writing a single storage byte, writing multiple storage bytes, reading a single storage byte, and reading multiple storage bytes. Each operation is shown in the figure below.

.. image:: images/13_media/image2.png
      
The following is an analysis of the various signal states and timing that occur during I2C bus communication.

① Bus Idle State

When both the SDA and SCL signal lines of the I2C bus are at a high level simultaneously, it is defined as the bus idle state. At this point, the output-stage field-effect transistors of all devices are in the cutoff state, meaning the bus is released, and the pull-up resistors on each signal line pull the levels high.

② Start Signal

While the clock line SCL remains at a high level, the level on the data line SDA is pulled low (i.e., a negative transition), which is defined as the start signal of the I2C bus. It marks the beginning of a data transfer. The start signal is actively generated by the master controller, and the I2C bus must be in an idle state before this signal is generated, as shown in the figure below.

.. image:: images/13_media/image3.png
      
③ Stop Signal

While the clock line SCL remains at a high level, the data line SDA is released, causing SDA to return to a high level (i.e., a positive transition), which is called the stop signal of the I2C bus. It marks the end of a data transfer. The stop signal is also actively generated by the master controller, and after this signal is generated, the I2C bus returns to the idle state.

④ Data Bit Transfer

Each data bit transferred on the I2C bus has a corresponding clock pulse (or synchronous control). Under the coordination of the SCL serial clock, each data bit is serially transferred bit by bit on SDA. During data transfer, while SCL is at a high level, the level on SDA must remain stable — a low level represents data 0, and a high level represents data 1. Only when SCL is at a low level is the level on SDA allowed to change state.

⑤ Acknowledge Signal (ACK and NACK)

All data on the I2C bus is transmitted in 8-bit bytes. After the transmitter sends each byte, it releases the data line during the 9th clock pulse, and the receiver feeds back an acknowledge signal. When the acknowledge signal is at a low level, it is defined as a valid acknowledge bit (ACK), indicating that the receiver has successfully received the byte.

When the acknowledge signal is at a high level, it is defined as a not-acknowledge bit (NACK), generally indicating that the receiver did not successfully receive the byte. For a valid ACK response, the receiver must pull the SDA line low during the low-level period before the 9th clock pulse and ensure it remains at a stable low level during the high-level period of that clock.

If the receiver is the master controller, after receiving the last byte, it sends a NACK signal to notify the slave transmitter to end data transmission and release the SDA line, so that the master receiver can send a stop signal.

Program Design
--------------

Although I2C timing is simple, poorly written code can cause many problems. On the open-source website http://opencores.org/, we can find many excellent code examples, most of which provide detailed documentation and simulation. As the saying goes, "stones from other hills may serve to polish jade" — properly using open-source code not only improves our development efficiency but also allows us to learn from others' development approaches. Since most code has been repeatedly modified and refined over a long period, some code may be difficult to understand. When you cannot fully understand someone else's code, the best approach is simulation.

.. image:: images/13_media/image5.png
      
From the IP core documentation, we learn that the i2c_master_byte_ctrl module mainly handles reading and writing of a single byte. We only need to complete the reading and writing of the device address, register address, data, etc., according to I2C read/write requirements.

The i2c_master_top module is a further encapsulation of the i2c_master_byte_ctrl module, handling the reading and writing of a single register. Since different device registers may be 8-bit or 16-bit, the i2c_addr_2byte signal is used here to control whether the register address is 8-bit or 16-bit.

For the i2c_master_top module state machine, if it is a write register operation, it first writes one byte of the device address (write operation), then writes 1 or 2 bytes of the register address, followed by one byte of data. If it is a read operation, it first writes one byte of the device address (write operation), then writes 1 or 2 bytes of the register address to complete the address write, then writes the device address again (read operation), and finally reads one byte of data. In any case, the program design must meet the chip's timing requirements, so it is best to carefully read the chip's datasheet before reading the program.

i2c_master_top Module Ports

The i2c_eeprom_test module handles the reading and writing of EEPROM. The EEPROM device address is A0. The program reads the data from address 00 and displays it via LEDs. When a key is pressed, the value is incremented by one, written back to the EEPROM, and displayed. In the I2C controller, most of the code functionality is also annotated in the comments.


 module i2c_eeprom_test(
     input            sys_clk,       //system clock 50Mhz on board
     input            rst_n,         //reset ,low active
     input            key,			//data will add 1 when push key
     inout            i2c_sda,		
     inout            i2c_scl,
     output [3:0]     led
 
 );
 localparam S_IDLE       = 0;
 localparam S_READ       = 1;
 localparam S_WAIT       = 2;
 localparam S_WRITE      = 3;
 reg[3:0] state;
 
 wire button_negedge;
 reg[7:0] read_data;
 reg[31:0] timer;
 
 wire scl_pad_i;
 wire scl_pad_o;
 wire scl_padoen_o;
 
 wire sda_pad_i;
 wire sda_pad_o;
 wire sda_padoen_o;
 
 reg[ 7:0] 	i2c_slave_dev_addr;
 reg[15:0] 	i2c_slave_reg_addr;
 
 reg 		i2c_write_req;
 wire 		i2c_write_req_ack;
 reg[ 7:0] 	i2c_write_data;
 
 reg 		i2c_read_req;
 wire 		i2c_read_req_ack;
 wire[7:0] 	i2c_read_data;
 
 assign led = ~read_data[3:0];
 
 ax_debounce ax_debounce_m0
 (
     .clk             (sys_clk),
     .rst             (~rst_n),
     .button_in       (key),
     .button_posedge  (),
     .button_negedge  (button_negedge),
     .button_out      ()
 );
  
 always@(posedge sys_clk or negedge rst_n)
 begin
     if(rst_n == 1'b0)
     begin
         state 				<= S_IDLE;
         i2c_write_req 		<= 1'b0;
         read_data 			<= 8'h00;
         timer 				<= 32'd0;
         i2c_write_data 		<= 8'd0;
         i2c_slave_reg_addr 	<= 16'd0;
         i2c_slave_dev_addr 	<= 8'ha0;//1010 000 0, device address
         i2c_read_req 		<= 1'b0;
     end
     else
         case(state)
             S_IDLE:
             begin
                 if(timer >= 32'd499_999)//wait 10ms
                     state <= S_READ;
                 else
                     timer <= timer + 32'd1;
             end
             S_READ:
             begin
                 if(i2c_read_req_ack)			//if read request ack, then i2c read data valid
                 begin
                     i2c_read_req <= 1'b0;
                     read_data	 <= i2c_read_data;
                     state 		 <= S_WAIT;
                 end
                 else
                 begin
                     i2c_read_req 		<= 1'b1;
                     i2c_slave_dev_addr 	<= 8'ha0;
                     i2c_slave_reg_addr 	<= 16'd0;
                 end
             end
             S_WAIT:
             begin
                 if(button_negedge)			//when push button, then data add 1, and switch to write state
                 begin
                     state 		<= S_WRITE;
                     read_data 	<= read_data + 8'd1;
                 end
             end
             S_WRITE:
             begin
                 if(i2c_write_req_ack)		//if write request ack, then switch to read state
                 begin
                     i2c_write_req 	<= 1'b0;
                     state 			<= S_READ;
                 end
                 else
                 begin
                     i2c_write_req 	<= 1'b1;
                     i2c_write_data 	<= read_data;
                 end
             end
             
             default:
                 state <= S_IDLE;
         endcase
 end
 //i2c bidirection control
 assign sda_pad_i = i2c_sda;
 assign i2c_sda = ~sda_padoen_o ? sda_pad_o : 1'bz;
 
 assign scl_pad_i = i2c_scl;
 assign i2c_scl = ~scl_padoen_o ? scl_pad_o : 1'bz;
 
 i2c_master_top i2c_master_top_m0
 (
     .rst					(~rst_n),
     .clk					(sys_clk),
     .clk_div_cnt			(16'd99),       	//Standard mode:100Khz; prescale = 50MHz/(5*100Khz) - 1
     
     // I2C signals 
     // i2c clock line
     .scl_pad_i				(scl_pad_i),        // SCL-line input
     .scl_pad_o				(scl_pad_o),        // SCL-line output (always 1'b0)
     .scl_padoen_o			(scl_padoen_o),     // SCL-line output enable (active low)
 
     // i2c data line
     .sda_pad_i				(sda_pad_i),        // SDA-line input
     .sda_pad_o				(sda_pad_o),        // SDA-line output (always 1'b0)
     .sda_padoen_o			(sda_padoen_o),     // SDA-line output enable (active low)
     
     
     .i2c_addr_2byte			(1'b0),   			//register address is 1 byte
     .i2c_read_req			(i2c_read_req),
     .i2c_read_req_ack		(i2c_read_req_ack),
     .i2c_write_req			(i2c_write_req),
     .i2c_write_req_ack		(i2c_write_req_ack),
     .i2c_slave_dev_addr		(i2c_slave_dev_addr),
     .i2c_slave_reg_addr		(i2c_slave_reg_addr),
     .i2c_write_data			(i2c_write_data),
     .i2c_read_data			(i2c_read_data),
     .error					()
 );
 ila_0 ila_m0 (
 	.clk		(sys_clk), 	// input wire clk
 	.probe0		(read_data) // input wire [7:0] probe0
 );
 endmodule

According to the IP core documentation, the I2C core uses a clock that is 5 times the SCL clock. If you want to obtain a 100KHz I2C clock, in this experiment the prescale value equals the reference clock 50MHz divided by 5*100KHz, minus 1, which is 99. This point should be noted.

Experiment Results
------------------

After downloading the experiment program, you can see the LEDs displaying a binary number. This number is the data stored at address 00 of the EEPROM, and the data is random. At this point, when the PL KEY2 button is pressed, the number increments by one and is written to the EEPROM. Downloading the program again, you can see that the updated data is directly displayed.

In the program, we have added a logic analyzer to observe the value of the read data. Each time the PL KEY2 button is pressed and run, you can see the data increase by 1.
